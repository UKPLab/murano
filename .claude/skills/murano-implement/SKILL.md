# Murano implement

Revise mode is adapted from `obra/superpowers` `skills/receiving-code-review@2ce8aa1`
(MIT): check each finding against the code before acting on it, push back with
evidence when it's wrong, and answer every item.

The rules are in `AGENTS.md`, and every section of it applies. The plan is the
`<!-- murano-dossier -->` comment on the issue.

## Implement mode (issue `agent:sourced`)

1. **Set up.** Add `agent:wip` to the issue.
   `git switch <base> && git pull --ff-only && git switch -c agent/<issue>-<slug>`,
   where `<base>` is `base_branch` in `.claude/agent-loop.json` (normally `main`).
   Open the PR against it: `gh pr create --base <base>`.
2. **Read before writing.** Read the dossier, `AGENTS.md`, and the two existing
   steps the dossier's mapping names, end to end, with their tests. Match their
   structure, docstring shape, naming and helper use.
3. **Tests first**, following `murano-test`. Watch the mechanism tests fail.
4. **Implement** at the size the dossier's mapping sets (`AGENTS.md` §1): a
   new option value on an existing step, a preset, or a new step module. If
   you find that a smaller rung covers the instrumental differences, use it
   and say why in the PR. If the license verdict is `adapt-ok`, adapt the
   pinned reference code. If it is `oracle-only`, write from the dossier's
   algorithm alone. End the module docstring with the `Attribution:` block
   (`AGENTS.md` §11); for an option on an existing step, add the method's
   paper and code to that step's docstring instead.
   - Wherever your code computes something differently from the reference
     code (or from the paper, when the code is oracle-only), put a comment on
     that line: `# Differs from <repo>@<sha> <path>: <what>, because <why>.`
     That includes incidental steps you dropped on purpose, such as a sign
     flip made unnecessary by computing an SVD directly.
5. **Register** it: go through `AGENTS.md` §8 item by item and record each item
   as done or "n/a, because …" for the PR body.
6. **Docs and notebooks** (`AGENTS.md` §10):
   - The guide section, CHANGELOG bullet and notebook markdown go through
     `humanizer` in embedded mode.
   - Execute the notebook: `uv run jupyter nbconvert --to notebook --execute --inplace <path>`.
   - If execution can't run here (no network for the GPT-2 weights, timeout),
     leave the notebook unexecuted and say so in the PR checklist. Never commit
     made-up outputs.
7. **Attribution:** add a `NOTICE.txt` line under "Adapted implementations".
   The notebook header cites the paper and the code at its pinned SHA.
8. **Checks:** all the commands in `AGENTS.md` §12 must pass. Then look at
   `git diff --stat <base>`. Every file listed has to be explained by the
   checklist. Revert anything else.
9. **Commit and open the PR.** Use conventional commits. Push the branch and
   create the PR with `gh pr create --base <base> --body-file <file>` (the
   repo's default branch may differ from `<base>`, so never omit `--base`).
   Write the body with `.claude/skills/write-pr-description/SKILL.md` on
   `.github/PULL_REQUEST_TEMPLATE.md`, then run it through `humanizer`. A
   maintainer has to take it in within a minute:
   - Everything above the collapsed checklist stays under 250 words. Being
     over means you are restating the diff, not that the PR is special.
   - The opening says what and why in one to three sentences.
   - "Needs a maintainer" holds only what a human must decide or check: a
     judgment call with a real alternative, an oracle that failed, something
     you could not run, a change outside the method's new files. One line
     each, naming the file or symbol. Everything you merely chose goes in a
     code comment or nowhere.
   - "Differences from the reference code": one line each, what and why,
     matching the `# Differs from` comments from step 4. The detail stays in
     the comments.
   - Never write a file or test inventory, mechanism the code comments
     already explain, dossier content, a defence of a choice nobody
     questioned, or a second statement of anything.
   - Tick only true checklist items. "n/a: <reason>" in at most ten words,
     nothing else.
   - Start the body with `> *Generated by the murano agent loop.*`
   - End it with `<!-- agent-review-round: 0 -->`
   - Labels: `enhancement`, `agent:needs-review`. On the issue, add `has-pr`
     and remove `agent:wip`.

Stop and label the issue `agent:blocked`, with a comment, when the dossier
turns out to be wrong or incomplete in a way you would have to guess around.

## Revise mode (PR `agent:changes-requested`)

1. Add `agent:wip`, then `gh pr checkout <n>` and `git pull --ff-only`.
2. Collect the work:
   - every numbered finding in the latest `<!-- murano-review -->` comment
   - every maintainer comment posted after it
   - any red CI (`gh pr checks <n>`, `gh run view --log-failed`)
3. For each item:
   1. Read the code it points at and check whether the finding holds.
   2. If it holds, fix it, adding or changing a test when the finding is about
      behaviour.
   3. If it doesn't hold, don't change code. Prepare a reply with evidence:
      file:line, a test that shows the behaviour, or the dossier or paper
      passage.
   - Don't fix findings from memory, don't batch unrelated fixes into one
     opaque commit, and don't "improve" code outside the findings.
4. Run every check in `AGENTS.md` §12, then push with no force.
5. Post one reply comment that answers each finding by number:
   `1. Fixed in <sha>: <one line>` or `2. Not changed: <evidence>`. Nothing
   else: no preamble, no recap.
   Then rewrite the PR body so it describes the branch as it is now (step 9's
   rules). Never append a revision log.
6. Increment `<!-- agent-review-round: N -->` in the PR body, then swap
   `agent:changes-requested` for `agent:needs-review` and remove `agent:wip`.

## Return

The PR URL, the checklist status, and anything left for a human (for example,
"notebook not executed").
